网络 I/O 模型对比 (以跳表引擎为例)

💡 核心发现

io_uring 优势

  • ✅ SQPOLL 模式消除系统调用开销，GET QPS 达到 57.8w
  • ✅ 相比 Epoll 提升 2.1 倍吞吐，延迟降低 52%
  • ✅ 相比 Redis 提升 6.5 倍吞吐，延迟降低 84%

存储引擎对比

  • 📊 三种引擎 GET 性能接近 (57-58w QPS)
  • 📊 SET 性能: 跳表 16.6w > 哈希 16.0w > 红黑树 15.5w
  • 📊 网络 I/O 是主要瓶颈，引擎差异影响较小

NtyCo 协程

  • 🔄 用户态协程，编程模型同步简洁
  • 🔄 性能略低于 Epoll，主要开销在协程切换
  • 🔄 P99 延迟较高 (7ms vs Epoll 4.5ms)

持久化开销

  • 💾 SET 需要写 WAL，性能约为 GET 的 30%
  • 💾 io_uring async WAL 减少同步写盘阻塞
  • 💾 与 Redis AOF (everysec) 策略一致

* QPS: 每秒查询数 (数值越大越好) | P50/P99: 50%/99% 请求的响应时间 (数值越小越好)

* 测试环境: Ubuntu 22.04, Linux 5.15, liburing 2.x | 持久化: io_uring async WAL

结论: io_uring (SQPOLL) 是高性能网络服务的最佳选择，相比 Redis GET 延迟降低 84%，吞吐提升 6.5x
